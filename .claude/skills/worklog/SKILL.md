# Worklog Skill

## 목적

하나의 기능 개발이 완료될 때마다 해당 기능의 개발 과정과 학습 내용을 기록한다.

작업일지는 단순한 개발 기록이 아니라,
나중에 사용자가 프로젝트를 다시 보면서 **무엇을 왜 만들었고 어떻게 동작하는지 복습할 수 있는 문서**를 만드는 것을 목적으로 한다.

## 실행 조건

다음 조건을 만족하면 작업일지를 작성한다.

* 하나의 기능 개발이 완료된 경우
* 하나의 주요 기술 구현이 완료된 경우
* 하나의 문제/오류를 해결한 경우 중 기록할 가치가 있는 경우

사소한 코드 수정이나 오타 수정에는 작업일지를 만들지 않는다.

## 저장 위치

프로젝트 루트의 다음 디렉터리를 사용한다.

```text
docs/worklogs/
```

기능별로 하나의 Markdown 파일을 생성한다.

파일명 예시:

```text
docs/worklogs/001-rss-collector.md
docs/worklogs/002-google-sheets-storage.md
docs/worklogs/003-policy-structuring.md
```

번호를 이용하여 기능 개발 순서를 확인할 수 있도록 한다.

## 작업일지 기본 형식

각 작업일지는 다음 구조를 따른다.

```markdown
# [기능명]

## 1. 한 줄 요약
이 기능이 무엇을 하는지 한 문장으로 설명한다.

## 2. 왜 만들었는가
프로젝트 전체 흐름에서 이 기능이 왜 필요한지 설명한다.

## 3. 구현한 것
실제로 무엇을 만들었는지 설명한다.

## 4. 동작 흐름
데이터가 어디에서 들어와서 어디로 이동하는지 설명한다.

예:
RSS
→ Python
→ 데이터 정제
→ Google Sheets
→ 다음 처리 단계

## 5. 주요 파일
해당 기능과 관련된 파일과 각 파일의 역할을 설명한다.

예:
- app/rss.py: RSS 데이터 수집
- app/sheets.py: Google Sheets 저장
- main.py: 실행 진입점

## 6. 핵심 코드 / 개념
기능을 이해하는 데 중요한 코드와 개념을 설명한다.

초보자가 이해할 수 있도록 쉬운 설명을 우선한다.

## 7. 사용한 기술
이번 기능에서 새롭게 사용한 기술, 라이브러리, API 등을 기록한다.

## 8. 문제와 해결
구현 과정에서 발생한 주요 오류나 문제를 기록한다.

- 문제:
- 원인:
- 해결:
- 배운 점:

## 9. 의사결정
구현 과정에서 선택한 중요한 결정과 그 이유를 기록한다.

예:
- 왜 PostgreSQL 대신 Google Sheets를 사용했는가?
- 왜 이 라이브러리를 선택했는가?

## 10. 배운 것
이번 기능을 구현하면서 새롭게 이해한 개념을 정리한다.

## 11. 현재 한계
현재 구현에서 부족하거나 임시로 처리한 부분을 기록한다.

## 12. 다음 단계
이 기능 이후 자연스럽게 이어지는 작업을 기록한다.
```

## 작성 원칙

### 1. 초보자 관점으로 작성

사용자가 나중에 코드를 다시 볼 때 이해할 수 있도록 작성한다.

전문 용어만 나열하지 않는다.

예:

잘못된 설명:

> Feed parser를 통해 RSS feed를 deserialize한다.

좋은 설명:

> RSS에서 가져온 글 목록을 Python이 다룰 수 있는 데이터 형태로 바꿔준다.

필요하면 그 아래에 정확한 기술 용어를 추가한다.

### 2. 코드보다 "왜"를 기록

코드를 그대로 복사하는 것보다 다음 내용을 중점적으로 기록한다.

* 왜 이 기능이 필요한가?
* 왜 이 방법을 선택했는가?
* 어떤 데이터를 다루는가?
* 어떤 문제가 있었는가?
* 어떻게 해결했는가?

### 3. 실제 구현과 다르게 작성하지 않는다

작업일지는 실제 프로젝트의 현재 상태를 기록한다.

구현하지 않은 기능을 구현한 것처럼 작성하지 않는다.
임의의 기술 선택이나 미래 계획을 실제 구현 내용처럼 기록하지 않는다.

### 4. 완료 시점의 상태를 기록

작업일지는 기능이 완료된 시점의 상태를 기준으로 작성한다.

기능이 이후 변경되면 새로운 작업일지 대신 기존 기록과 별도로 변경 내용을 기록할 수 있다.

## 완료 후 체크

작업일지를 작성한 뒤 다음 내용을 확인한다.

* 이 기능의 목적을 설명할 수 있는가?
* 데이터 흐름을 설명할 수 있는가?
* 주요 파일의 역할을 설명할 수 있는가?
* 새롭게 배운 개념을 설명할 수 있는가?
* 발생했던 주요 문제와 해결 방법이 기록되어 있는가?
* 다음 작업이 무엇인지 알 수 있는가?

## 중요한 원칙

작업일지는 **개발자용 공식 문서처럼 어렵게 작성하지 않는다.**

사용자가 1~2개월 후 다시 읽었을 때
"아, 내가 이때 이런 이유로 이렇게 구현했구나."
라고 기억을 되살릴 수 있는 수준으로 작성한다.

작업일지를 작성하기 위해 기능 개발 방식을 바꾸거나,
불필요하게 긴 내용을 추가하지 않는다.
