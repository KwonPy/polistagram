## 1. 전체 구조

```
금융위 RSS
   ↓
articles_raw       1계층  원본        LLM 없음, 전 건 저장
   ↓  status = active 인 것만
articles_triage    2계층  분류        짧은 LLM 1회
   ↓  personal_relevance 로 갈라짐
articles_detail    3계층  상세        긴 LLM 1회, 일부만
   ↓
개인화             저장 안 함, 사용자 요청 시 생성
```

**왜 3층으로 나누는가:** 30건 중 개인이 직접 행동할 수 있는 문서는 **5건(17%)**뿐이었다.
전부 상세 추출하면 Gemini 무료 할당량이 낭비되고, 근거 없는 문서에서 AI가 없는 사실을 지어낸다.
1계층만 만들어도 "새 정책 목록" 서비스는 동작한다.

### 처리 게이트 (3계층 진입 기준)

`doc_type`이 아니라 **`personal_relevance`로 결정한다.**

| `personal_relevance` | 처리 | 30건 기준 |
|---|---|---|
| `direct` | 3계층 **8개 필드 전체** 추출 | 5건 |
| `indirect` | `summary_easy` **하나만** | 약 12건 |
| `none` | 3계층 **스킵** | 약 13건 |

**왜 doc_type이 아닌가 — 실측 반례 2건**

| 문서 | doc_type | doc_type 기준이면 | 실제 |
|---|---|---|---|
| 87554 금융권 채용박람회 | `info` | 요약만 (버림) | 청년에게 **날짜·장소·홈페이지까지 있는 최고 관련 문서** |
| 87569 초장기기술투자펀드 | `support_program` | 전체 추출 | 운용사(VC/PE) 대상, **개인 완전 무관** |

`doc_type`으로 처리 깊이를 정하면 **가장 쓸모 있는 문서를 버리고 쓸모없는 문서에 토큰을 쓴다.**

## 2. 1계층 — `articles_raw`

LLM을 쓰지 않는다. RSS에서 가져온 그대로 저장한다.

| 필드 | 타입 | 설명 |
|---|---|---|
| `article_id` | string | **PK.** 원문 주소 끝 숫자 (`87646`) |
| `title` | string | RSS `title` |
| `source_url` | string | RSS `link` |
| `published_at` | `YYYY-MM-DD` | RSS `updated`의 날짜 부분만 (시각은 항상 `00:00:00`이라 버림) |
| `body_text` | string | 8절 규칙으로 뽑은 본문 |
| `body_char_count` | int | 본문 없는 문서 판정용 |
| `content_hash` | string | `body_text`의 SHA-256 앞 16자. 나중에 변경 감지용 |
| `collected_at` | ISO datetime | 수집 시각 |
| `status` | `active` \| `skipped_no_body` | **300자 미만이면 skip.** ID는 남겨 재수집 방지 |

**`article_id`가 왜 URL 끝 숫자인가:** RSS에 고유번호 필드가 따로 없다.

```
https://www.fsc.go.kr/no010101/87646
                                └── 이 숫자가 사실상 ID
```

**`status`가 왜 필요한가:** 30건 중 3건은 본문이 사실상 없었다. 한 건은 전체가 23자였다.

> 자세한 내용은 첨부파일 참고 부탁드립니다.

내용이 `.hwp`/`.pdf` 첨부에만 있는 문서다. 여기에 AI를 돌리면 **근거가 없으니 지어낸다.**
그래서 걸러내되, 다음 수집 때 또 가져오지 않도록 **ID는 남긴다.**

## 3. 2계층 — `articles_triage`

`status = active`인 문서에만 **짧은 LLM 호출 1회**를 돌린다.

| 필드 | 타입 | 설명 |
|---|---|---|
| `article_id` | string | 1계층과 연결 |
| `doc_type` | 아래 5개 중 1개 | 문서 성격 (**UI 라벨 용도**) |
| `topics` | 아래 10개 중 복수 | **매칭의 주력** |
| `personal_relevance` | `direct` \| `indirect` \| `none` | **처리 게이트** |
| `one_line_summary` | string | 한 문장 |
| `audience_groups` | 아래 5개 중 복수 \| 빈 목록 | 정책이 특정 직업군을 콕 집어 대상으로 할 때만 채운다. 일반 대상이면 빈 목록 |

### `doc_type` (5개)

| 값 | 뜻 | 30건 |
|---|---|---|
| `support_program` | 지원·혜택 프로그램 | 6 |
| `rule_change` | 제도·규정·**법률** 변경 | 8 |
| `plan` | 계획·방향 발표 | 6 |
| `info` | 통계·회의·행사·캠페인 안내 | 9 |
| `admin` | 제재·인사·시험 등 행정공지 | 4 |

**왜 10개에서 5개로 줄였나**

1. `doc_type`은 개인화에 쓰이지 않는다. 게이트를 `personal_relevance`가 맡으면 남는 역할은 **화면 배지 하나**다.
2. 30건 중 **1건뿐인 값이 2개** 있었다 (`approval_case`, `rule_notice`).
3. 이번에 "법률 개정안 국회 본회의 통과"가 3건 나왔다 (87572·87571·87570). 새 값을 만들면 11개가 되는데,
   개인 입장에선 규정 변경과 똑같이 **"제도가 바뀐다"**라서 `rule_change`로 흡수했다.
4. 값이 한 개로 안 떨어지는 문서가 있다 — 87543은 *통계 + 회의*, 87521은 *규정 변경 + 설명회*.
   값이 적을수록 LLM이 덜 흔들린다.

### `topics` (8개, 복수 선택)

```
대출 / 주거·전세 / 저축·자산형성 / 투자·주식
보험 / 창업·사업자금 / 취업·채용 / 기타
```

30건 원문에 실제로 등장한 주제만 넣었다. 추측으로 만든 값은 없다.

| 변경 | 이유 |
|---|---|
| ➕ `취업·채용` | 87554(채용박람회), 87628(회계사시험) |
| ➖ `금융교육` | 30건 중 1건뿐이고 `사기예방`과 겹침 |
| ➖ `가상자산`, `사기예방`, `신용·연체` → `기타`로 통합 | 사용자 관심분야(`interests`)로 노출할 만큼 범용적이지 않다고 판단. **개인화 필터링 대상에서 뺀다** |

**왜 세 값을 없애지 않고 `기타`로 통합했나**

`topics`는 3절이 아니라 5절 `interests`와 어휘를 맞춰야 하는 필드다. 즉 여기 값은 전부
"사용자가 관심분야로 고를 만한 범용 주제"여야 한다. `가상자산`·`사기예방`·`신용·연체`는

- 특정 사고/사건성 이슈(사기예방)이거나
- 특정 자산군(가상자산)이거나
- 특정 신용 상태(신용·연체)에 국한돼

일반적인 "관심분야" 개념과 맞지 않는다. 그렇다고 값 자체를 지우면 87521·87499 같은 문서가
`topics = []`가 되어 2계층 분류에서 붕 뜬다. 그래서 가는 값은 지우되, 해당 문서들은
`기타`로 묶어 **분류는 유지하고 개인화 매칭에서만 제외**한다.

`기타`는 5절 `interests` 선택지에는 넣지 않는다. 아무도 "기타"를 관심사로 고르지 않으므로,
`기타`만 붙은 문서는 6절 교집합 매칭에서 자동으로 걸러진다 — 별도 예외 처리가 필요 없다.

### `audience_groups` (5개, 복수 선택, 빈 목록 허용)

```
근로자 / 구직자 / 소상공인·자영업자 / 대학생 / 프리랜서·특수고용직
```

정책이 **특정 직업군을 콕 집어 대상으로 할 때만** 채운다. 일반 국민 대상 정책은 빈 목록으로 둔다.

5절 `occupation_type`과 어휘를 맞춘 필드다 — 사용자가 고르는 값과 정책이 요구하는 값이
같은 말이어야 매칭이 집합 연산으로 끝난다 (`topics`/`interests` 관계와 동일한 설계).

**왜 이 5개인가 (10절 (2)(3) 해결)**

기존에 후보로 뒀던 12개 값 중:

| 제외 | 이유 |
|---|---|
| 청년, 고령층, 아동·청소년 | `birth_date`로 나이를 이미 계산할 수 있어 중복 |
| 신혼부부, 무주택·임차인, 중·저신용자, 취약계층, 금융피해자 | 고정 입력 항목(지역/성별/생년월일/개인특성)만으로는 유도 불가능 |
| 군복무자 | 실측 30건 중 1건뿐 — 범용성 낮음 |
| 사회초년생 | `근로자`·`구직자`와 의미가 겹쳐 매칭에 새 정보를 안 줌 |

남긴 5개는 전부 **사용자가 스스로 고를 수 있는 범용 직업 상태**이자, 실제 정책 대상으로
자주 등장하는 값이다. 여기 안 걸리는 사람(전업주부, 은퇴자 등)은 `occupation_type`을
비워두면 되고, 이 경우 7절 매칭에서 이 축은 그냥 채점에서 빠진다 — 억지로 캐치올 값을
만들지 않는다.

### `personal_relevance`

| 값 | 기준 |
|---|---|
| `direct` | 개인이 **지금 신청·이용·신고할 수 있는 것**이 있다 |
| `indirect` | 개인에게 영향은 있으나 **당장 할 행동이 없다** |
| `none` | 기관·업계 대상 |

## 4. 3계층 — `articles_detail`

`personal_relevance = direct`인 문서만 **긴 LLM 호출 1회**로 8개 필드를 뽑는다.
`indirect`는 `summary_easy` 하나만 채우고 나머지는 비운다.

| 필드 | 타입 | 규칙 |
|---|---|---|
| `article_id` | string | |
| `summary_easy` | string | 쉬운 말 3~5문장 |
| `target` | string | 누가 대상인가. **원문 표현 기반** |
| `benefit` | string \| null | 무엇을 받는가 |
| `how_to_apply` | string \| **null** | **원문에 있을 때만. 없으면 반드시 null** |
| `key_dates` | string[] | **원문 표현 그대로** |
| `deadline` | `YYYY-MM-DD` \| null | **명확한 마감일이 있을 때만** |
| `region_scope` | string[] \| null | 지역 한정 정책만. 전국이면 null |
| `evidence_quotes` | string[] | 근거 문장 2~3개 |

### `key_dates`와 `deadline`을 나눈 이유

원문 날짜가 이렇게 애매하다.

```
"연말부터 투자집행을 개시"
"'27년 하반기"
"10월까지 운용사를 최종 선정"
```

이걸 억지로 ISO 날짜로 바꾸면 **사용자에게 거짓 마감일을 알리게 된다.**

그래서 **사람이 볼 것과 기계가 쓸 것을 분리한다.**

```json
"key_dates": ["9.1일 지자체 보험상품 출시", "10월까지 운용사 선정", "연말부터 투자집행"],
"deadline": null
```

- `key_dates` — 화면에 그대로 보여준다. 원문 표현이라 거짓말이 안 된다.
- `deadline` — 코드가 쓴다. **확실한 날짜가 있을 때만** 채운다.

**`deadline`이 왜 꼭 필요한가:** 87554 채용박람회는 8/19~20에 **이미 끝났다.**
오늘(9/5) 사용자에게 "당신에게 관련된 정책"으로 보여주면 안 된다.

```python
if article["deadline"] and article["deadline"] < TODAY:
    continue    # 마감 지난 건 추천에서 뺀다
```

### `how_to_apply`가 null을 허용하는 이유

30건 중 개인 관련 1위 문서조차 **개인 신청 절차가 원문에 없었다.**
87566(수해 지원)은 본문이 `[별첨] 상세내용`으로 끝난다.

필드를 만들면 AI는 그 칸을 채우려 한다. **근거 없는 필드는 편의 기능이 아니라 환각 발생 장치다.**
그래서 "없으면 반드시 null"을 프롬프트에 명시한다.

### 기존 초안에서 뺀 필드

| 뺀 것 | 이유 |
|---|---|
| `conditions` | `target`과 내용이 겹쳤다. 실측에서 둘 다 한 문장이었다 |
| `related_orgs` | 30건 어디에서도 개인화에 쓸 데가 없었다 |
| `status_policy` | 5개 값이 `deadline` + `key_dates`와 중복 |
| `audience_scope` | `personal_relevance`와 거의 같은 정보 |
| `source_completeness` | `how_to_apply = null`이 같은 역할을 한다 |

**10개 → 8개.** 필드를 줄인 만큼 LLM이 지어낼 칸도 줄었다.

## 5. 사용자 프로필

입력 항목은 **아래 4개로 고정**한다. 더 늘리지 않는다.

```json
{
  "user_id": "string",
  "email": "string",
  "region": "경기",
  "gender": "여성",
  "birth_date": "2002-05-18",
  "occupation_type": "대학생",
  "interests": ["저축·자산형성", "투자·주식"],
  "notify_email": true
}
```

| 필드 | 타입 | 설명 |
|---|---|---|
| `region` | string | 거주지역 |
| `gender` | `남성` \| `여성` | |
| `birth_date` | `YYYY-MM-DD` | **생년월일 전체.** `birth_year`(연도만)에서 변경 — 만 나이 계산에 필요 |
| `occupation_type` | 아래 5개 중 1개 \| null | 개인 특성. 해당 없으면 비워둔다 |
| `interests` | 3절 `topics` 7개(`기타` 제외) 중 복수 | 관심분야. **어휘가 같아야 매칭이 집합 연산으로 끝난다** |

### `occupation_type` (5개, 단일 선택)

```
근로자 / 구직자 / 소상공인·자영업자 / 대학생 / 프리랜서·특수고용직
```

3절 `audience_groups`와 어휘를 맞춘 값이다. 근거와 제외 이유는 3절 `audience_groups` 항목 참고.

**청년 키워드를 왜 안 넣었나:** `birth_date`로 만 나이를 계산하면 "청년(만 19~34세)" 여부는
코드로 바로 판정된다. 프로필에 별도 값을 두면 생년월일과 중복되고, 지자체마다 다른
청년 나이 기준(정책마다 다름)을 반영하기도 오히려 이쪽이 유리하다.

## 6. 매칭 로직 (LLM 없음)

```python
def score(profile, article):
    """사용자와 정책이 얼마나 맞는지 점수로 만든다."""
    if article["deadline"] and article["deadline"] < TODAY:
        return 0                                    # 마감 지남
    if article["region_scope"] and profile["region"] not in article["region_scope"]:
        return 0                                    # 지역 안 맞음
    if (article["audience_groups"] and profile["occupation_type"]
            and profile["occupation_type"] not in article["audience_groups"]):
        return 0                                    # 특정 직업군 대상인데 나는 해당 안 됨
    return len(set(profile["interests"]) & set(article["topics"]))
```

한 줄씩 읽으면:

- `if article["deadline"] and ...` : 마감일이 **있고**, 그게 오늘보다 **이전**이면 0점 → 안 보여준다.
- `if article["region_scope"] and ...` : 지역 한정 정책인데 내 지역이 아니면 0점.
- `if article["audience_groups"] and profile["occupation_type"] and ...` : 정책이 **특정 직업군을 콕 집었고**,
  내 `occupation_type`도 **정해져 있는데**, 그 목록에 내가 없으면 0점.
  둘 중 하나라도 비어 있으면(정책이 일반 대상이거나, 내가 직업 특성을 안 밝혔거나) 이 축은 그냥 건너뛴다 — 억지로 걸러내지 않는다.
- `set(A) & set(B)` : 두 목록의 **겹치는 항목**만 남긴다. (`&` = 교집합)
- `len(...)` : 겹친 개수가 곧 점수다. 관심사가 많이 겹칠수록 높다.

**쉽게 말하면:** "내 관심사와 정책 주제가 몇 개나 겹치나"를 센다.

`CLAUDE.md` 6절 *"명확한 로직은 일반 코드로, LLM은 해석과 설명에 집중"*에 맞춘 구조다.
**LLM은 매칭에 관여하지 않는다.** 매칭된 뒤 "왜 관련 있는지" 설명할 때만 부른다.

## 7. Google Sheets 저장 규칙

Sheets 칸 하나에는 글자만 들어간다. 목록과 빈 값을 어떻게 넣을지 정한다.

| 타입 | 저장 방법 | 예 |
|---|---|---|
| 문자열 목록 | **파이프(`\|`)로 이어붙인다** | `대출\|주거·전세` |
| null | **빈 칸** | (아무것도 안 씀) |
| 날짜 | `YYYY-MM-DD` | `2026-09-01` |
| 불리언 | `TRUE` / `FALSE` | |

```python
cell = "|".join(topics)                     # 저장: ["대출","보험"] → "대출|보험"
topics = cell.split("|") if cell else []    # 읽기: "대출|보험" → ["대출","보험"]
```

- `"|".join(목록)` : 목록의 항목들 **사이에** `|`를 끼워 하나의 글자로 만든다.
- `cell.split("|")` : 반대로 `|`를 기준으로 잘라 다시 목록으로 만든다.
- `if cell else []` : 칸이 비어 있으면 빈 목록을 준다. (빈 글자를 자르면 `[""]`가 나와서 버그가 된다)

**왜 JSON이 아닌가:** Sheets를 열었을 때 **눈으로 바로 읽히는 게** MVP에 훨씬 중요하다.
파싱도 `split("|")` 한 줄이면 끝난다. 어휘가 고정돼 있어 값에 `|`가 들어갈 일이 없다.

3계층에서 객체 배열(`key_dates`)을 문자열 배열로 바꾼 덕분에 **JSON이 필요한 칸이 하나도 없다.**

## 8. 본문 추출 규칙 (v3) — 확정

금융위는 `<table>`을 **표가 아니라 강조 박스로 쓴다.**
그래서 "표 모양인가"가 아니라 **"격자형 데이터인가"**로 판정한다.

```python
def is_data_table(table):
    """격자형 데이터 표인가? (True면 본문에서 제거)"""
    trs = table.find_all("tr")

    if len(trs) < 2:                      # v3에서 추가: 1행짜리는 섹션 제목 박스
        return False

    n_cols = max(len(tr.find_all(["td", "th"])) for tr in trs)
    cells = [c.get_text(" ", strip=True) for tr in trs for c in tr.find_all(["td", "th"])]
    cells = [c for c in cells if c]
    if not cells:
        return True

    avg = sum(len(c) for c in cells) / len(cells)

    if n_cols < 2:                        # 열이 1개면 표가 아니라 박스
        return False
    return (n_cols >= 3 and avg < 40) or avg < 15
```

한 줄씩 읽으면:

- `trs = table.find_all("tr")` : 표의 **행**을 모두 찾는다. (`tr` = table row)
- `if len(trs) < 2: return False` : **행이 2개보다 적으면 표가 아니다.** 진짜 데이터표는 헤더 + 데이터라 최소 2행이다.
- `n_cols = max(...)` : 각 행의 칸 수를 세서 **가장 많은 열 개수**를 구한다.
- `avg = ...` : **칸 하나당 평균 글자 수**.
- `if n_cols < 2: return False` : 열이 1개면 박스이므로 살린다.
- `return (n_cols >= 3 and avg < 40) or avg < 15` : 열이 여럿인데 칸이 짧으면 진짜 표.

### v2 → v3에서 무엇이 바뀌었나

`len(trs) < 2` 한 줄을 추가했다. v2는 이런 것들을 **잘못 지우고 있었다.**

```
1  2026년 7월 가계대출 동향          ← 3열, 평균 8자 → 데이터표로 오판
2  확대 가계부채 점검회의 개최
1  추진배경 및 현황
```

섹션 제목을 3칸짜리 `<table>`로 그린 것이라 열이 많고 글자가 짧아 격자로 잡혔다.
공통점은 **행이 1개**뿐이라는 것이었다.

### 30건 전수 검증

| 항목 | 결과 |
|---|---|
| 문서 | 30건 |
| `<table>` 총 개수 | 116개 |
| v2가 제거 | 26개 (**9개 오분류**) |
| v3가 제거 | **17개 (오분류 0건)** |

v3가 남긴 17개는 눈으로 전부 확인했다 — 가계대출 증감 추이, 회계사시험 합격률,
펀드 출자계획 등 **전부 진짜 숫자 격자**였다.

**표를 지워도 정보는 안 사라진다.** 본문에 같은 내용이 서술로 남기 때문이다.
