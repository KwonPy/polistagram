# 스키마 확정 — 실측 기반에서 범용 최소 구조로 전환

> 작성일: 2026-09-06
> 관련 문서: [docs/schema.md](../schema.md), [001-schema-design.md](001-schema-design.md)

---

## 1. 한 줄 요약

실측 데이터(30건)를 따라가며 스키마를 정교화하다 보니 값의 개수가 계속 늘어났고, 그만큼 예외 케이스도 늘어 스키마가 복잡해졌다. 그래서 방향을 바꿔 `topics`와 사용자 프로필을 처음부터 적은 개수의 범용 값으로 다시 짜고 확정했다.

## 2. 왜 했는가

001에서 20건 표본으로 방향만 논의했던 스키마를, 30건 실측으로 채워가며 `topics` 10개, `doc_type` 5개 등으로 구체화했다. 문제는 이 방식이 **"원문에 이 표현이 나왔으니 값을 추가한다"**를 반복하는 구조라는 점이다. 값이 늘수록:

- 사용자가 관심사로 고를 수 있는 범위(어휘)도 같이 늘어야 하고
- 값 하나하나가 실제로 몇 건이나 커버하는지 다시 확인해야 하고
- 소수 사례(1~2건)를 위한 값과 자주 등장하는 값이 뒤섞여 매칭 로직에 예외가 생긴다

그래서 판단을 바꿨다: **처음부터 적은 수의 범용 값으로 커버가 되는지 먼저 확인**하고, 안 되는 부분만 나중에 늘리는 게 낫다.

## 3. 구현한 것

⚠️ 이번에도 서비스 코드가 아니라 `docs/schema.md` 문서 확정 작업이다.

- `topics`: 10개 → **8개**. `가상자산`·`사기예방`·`신용·연체` 제거, 해당 문서는 `기타`로 통합 (값을 지우지 않고 개인화 매칭 대상에서만 뺌)
- 사용자 프로필: 입력 항목을 **`region`/`gender`/`birth_date`/`occupation_type`/`interests` 5개로 고정**
- `occupation_type` ↔ `audience_groups`: 어휘를 **5개(근로자/구직자/소상공인·자영업자/대학생/프리랜서·특수고용직)로 통일**
- 매칭 로직(`score` 함수)에 `occupation_type ↔ audience_groups` 교집합 필터 추가 — `region_scope`와 동일하게 "둘 다 값이 있을 때만 걸러낸다" 패턴

## 4. 동작 흐름

```
정책 원문
  ↓  LLM (짧은 호출)
topics(8개) + audience_groups(5개) 분류
  ↕  어휘를 맞춰둔 매칭
사용자 프로필: interests(7개) + occupation_type(5개)
  ↓  집합 연산 (LLM 없음)
교집합 점수 → 관련 정책 노출
```

## 5. 주요 파일

- `docs/schema.md`: 확정된 스키마 전체. 이번 변경도 여기 반영됨.
- 서비스 코드는 아직 없다.

## 6. 핵심 코드 / 개념

**"기타로 묶는다"는 패턴.** 값을 아예 지우면 그 값만 붙어있던 문서가 `topics = []`가 되어 분류 자체가 붕 뜬다. 그래서 값은 지우되, 분류는 유지하고 **매칭(개인화)에서만 제외**하는 방식을 썼다.

```python
# 기타만 붙은 문서는 사용자가 '기타'를 관심사로 고르지 않으므로
# 교집합 매칭에서 자연히 걸러진다 — 별도 예외 코드가 필요 없다.
score = len(set(profile["interests"]) & set(article["topics"]))
```

같은 원리를 `occupation_type`에도 적용했다: 5개 어디에도 안 걸리는 사람은 그냥 값을 비워두면 되고, 매칭 함수는 값이 있을 때만 필터링한다.

## 8. 문제와 해결

- **문제:** 실측 기반으로 값을 하나씩 추가하다 보니 `topics` 9→10개, `doc_type` 10→5개처럼 항목 수가 계속 흔들리고, 그때마다 사용자 프로필도 같이 손봐야 했다.
- **원인:** "원문에 나왔으니 값을 만든다"는 접근이 **커버리지는 늘지만 일반화는 안 되는** 방식이었다. 1건짜리 값(`가상자산`, `군복무자` 등)까지 정식 값으로 취급하니 관심사/프로필 선택지가 지저분해졌다.
- **해결:** 값을 늘리는 대신, 사용자가 실제로 관심사·특성으로 고를 만한 **범용 값만 남기고 나머지는 `기타`/빈 값으로 흡수**했다.
- **배운 점:** 실측 데이터는 "이 값이 실제로 등장하는가"를 검증하는 데는 필수지만, **"이 값을 스키마에 넣을 것인가"는 별개 판단**이다. 등장했다고 다 넣으면 스키마가 데이터를 따라 무한히 커진다.

## 9. 의사결정

- **왜 `가상자산`/`사기예방`/`신용·연체`를 지우지 않고 `기타`로 묶었나** — 지우면 해당 문서의 분류가 비어버린다. 분류는 유지하되 개인화 매칭 후보에서만 빼는 게 안전하다.
- **왜 `occupation_type`/`audience_groups`를 5개로 확정했나** — 기존 12개 후보 중 청년/고령층/아동청소년은 `birth_date`로 이미 계산 가능해 중복이고, 신혼부부·무주택자 등은 고정 입력 4항목만으로 유도가 안 되며, 군복무자는 실측 빈도가 1건뿐이라 범용성이 낮다고 판단했다.
- **왜 사용자 프로필을 5개 필드로 고정했나** — 입력 항목이 늘어날수록 사용자 이탈이 커지고, 늘린 만큼 매칭 로직도 복잡해진다. 최소 구성으로 먼저 커버리지를 확인하기로 했다.

## 10. 배운 것

**실측 기반 설계와 범용 설계는 트레이드오프 관계다.** 001에서 배운 "스키마는 상상이 아니라 데이터에서 나온다"는 원칙은 여전히 맞지만, 데이터를 따라가기만 하면 값이 끝없이 늘어난다는 반작용이 있다는 걸 이번에 확인했다. **처음에는 적은 수의 범용 값으로 스키마를 짜고, 실제로 커버가 안 되는 부분이 드러날 때만 값을 추가하는 순서가 더 안전하다.**

## 11. 현재 한계

| 한계 | 내용 |
|---|---|
| 커버리지 재검증 안 됨 | 8개/5개로 줄인 값이 30건 실측을 실제로 얼마나 커버하는지 다시 세어보지 않았다 |
| `gender` 미사용 | 프로필에 추가했지만 아직 매칭 로직(`score`)에는 반영 안 함 — 성별 특정 정책이 표본에 없었다 |
| `region_scope` 표기 통일 미해결 | "경남"/"경상남도" 등 표기가 섞여 있는 문제는 여전히 남아 있다 |
