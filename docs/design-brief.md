# Polistagram 디자인 브리프

> 작성일: 2026-09-12
> 관련 문서: [CLAUDE.md](../CLAUDE.md), [schema.md](schema.md), [004-landing-page.md](worklogs/004-landing-page.md)
> 상태: 초안 — 카드 피드 화면 작업 전에 방향을 맞추기 위한 문서. 미정 항목은 8절에 모아둠.

---

## 1. 한 줄 정의

**"인스타그램 피드처럼 넘겨보는 금융정책 카드뉴스."**

사용자가 프로필을 한 번 입력하면, 자신과 관련 있는 금융정책만 카드 한 장 단위로 받아본다.

## 2. 이 서비스가 아닌 것

디자인 방향을 잡기 전에, 혼동하기 쉬운 비교 대상과의 차이를 분명히 한다.

| 이것이 아니다 | 왜 |
|---|---|
| 정책 검색 엔진 | 검색창·필터 UI 중심이 아니다. 사용자가 찾는 게 아니라 서비스가 골라준다 |
| 정부 정책 포털 (정부24 등) | 표·목록형 정보 나열이 아니다. 카드 한 장으로 소화되는 형태다 |
| 알림/푸시 서비스 | 알림을 발송하지 않는다. 피드에 접속했을 때 반영돼 있으면 된다 ([CLAUDE.md](../CLAUDE.md) 1절) |
| 뉴스 요약 앱 | 단순 요약이 목적이 아니라 "나에게 관련 있는가 + 무엇을 해야 하는가"까지 안내한다 |

## 3. 타깃 사용자와 톤

* **1차 타깃**: 금융정책 용어가 낯설고, 정책이 나와 관련 있는지 스스로 판단하기 어려운 일반 사용자 (대학생, 사회초년생, 프리랜서 등 — [schema.md](schema.md) 5절 `occupation_type` 참고)
* **톤**: 딱딱한 공문서 톤이 아니라, 친구가 "이거 너한테 해당되는 거 아냐?"라고 짚어주는 톤
* **신뢰도**: 정책 정보를 다루므로 가볍되 신뢰감을 잃으면 안 된다. 원문 링크를 항상 붙여 "이 서비스가 지어낸 말이 아니다"를 보여준다 ([schema.md](schema.md) `evidence_quotes` 참고)

### 한눈에 요약

| 항목 | 내용 |
|---|---|
| **주 사용자** | 금융정책 이해·판단이 어려운 2030 대학생·사회초년생·프리랜서 |
| **언제/어디서** | 이동 중·자투리 시간에, 모바일 화면으로 짧게 훑어볼 때 |
| **가장 중요한 일** | "이 정책이 나와 관련 있는지" 바로 알고, 관련 있으면 "무엇을 해야 하는지" 바로 아는 것 |

## 4. 핵심 사용자 흐름

```
프로필 입력 (최초 1회, 완료됨)
   ↓
카드 피드 진입
   ↓
카드 한 장 = 정책 하나
   ↓
스와이프/스크롤로 다음 카드
   ↓
"자세히 보기" → 원문 또는 행동 단계 펼침
```

지금까지: **프로필 입력 폼까지 완료** ([004-landing-page.md](worklogs/004-landing-page.md)). 이 브리프는 다음 화면인 **카드 피드**를 준비하기 위한 것이다.

## 5. 카드 한 장의 정보 구조

`schema.md` 3·4계층 필드를 화면 요소로 매핑한다. `personal_relevance`에 따라 카드에 담기는 정보량이 다르다는 점이 중요하다 — 모든 카드가 같은 두께가 아니다.

### 공통 (모든 카드)

| 화면 요소 | 데이터 출처 | 비고 |
|---|---|---|
| 분야 배지 | `doc_type` | 예: "지원제도", "제도 변경" |
| 한 줄 제목 | `one_line_summary` | 카드 첫인상 |
| 관련 태그 | `topics` ∩ 사용자 `interests` | 겹치는 것만 하이라이트 |
| 원문 링크 | `source_url` | 항상 노출 — 신뢰의 근거 |

### `direct` (신청/행동 가능 — 카드가 가장 두껍다)

| 화면 요소 | 데이터 출처 |
|---|---|
| 쉬운 설명 | `summary_easy` |
| 대상 | `target` |
| 혜택 | `benefit` |
| 신청 방법 | `how_to_apply` (null이면 이 섹션 자체를 숨긴다 — 없는 정보를 억지로 채우지 않는다) |
| 일정 | `key_dates` (원문 표현 그대로 노출), `deadline` 지났으면 애초에 피드에 안 보임 |
| 행동 단계 | 자격 확인 → 서류 확인 → 신청 방법 확인 → 신청 기간 확인 ([CLAUDE.md](../CLAUDE.md) 4절 ⑥) |

### `indirect` (참고용 — 카드가 얇다)

| 화면 요소 | 데이터 출처 |
|---|---|
| 쉬운 설명 | `summary_easy`만 |
| CTA | "자세히 보기" 대신 "원문에서 확인" — 행동 단계 섹션 자체가 없음 |

**디자인 원칙:** `direct`와 `indirect`를 시각적으로 구분한다. 사용자가 "이건 지금 뭔가 할 수 있는 카드구나"를 한눈에 알아야 한다 (예: `direct`는 액션 버튼이 있고, `indirect`는 없다).

## 6. 왜 이 정책이 나와 관련 있는가 (관련성 설명)

`CLAUDE.md` 4절 ⑤에 명시된 핵심 기능. 매칭 점수(`schema.md` 6절)를 그대로 숫자로 보여주지 않는다 — "관심사 2개 일치"가 아니라 "당신이 관심 있다고 한 **저축·자산형성**과 관련된 정책이에요" 같은 자연어 한 문장으로 노출한다. 이 문장 생성이 Gemini의 역할이다.

## 7. 비주얼 방향 (Pico.css 기반)

프론트엔드는 이미 확정됨 (`CLAUDE.md` 11절): 빌드 도구 없는 단일 HTML + Pico.css CDN. 이 브리프는 그 제약 안에서의 방향만 제안한다.

* **레이아웃**: Pico.css의 `container`를 그대로 쓰되, 카드 피드는 세로로 쌓이는 카드 리스트 (인스타그램 피드형) — 좌우 스와이프 캐러셀보다 구현이 단순하고 모바일에 자연스럽다
* **카드 컴포넌트**: Pico.css에는 전용 카드 클래스가 없으므로 `<article>` 태그를 그대로 카드로 쓴다 (Pico가 기본 스타일링해줌) — 새 CSS 프레임워크를 추가하지 않는다
* **색상**: Pico.css 기본 테마 유지, 배지 색상만 `doc_type`별로 최소한의 구분 (예: 지원제도=초록 계열, 제도 변경=파랑 계열) — 색 종류를 늘리지 않고 5개 `doc_type`에 맞춰 5색 이하로 제한
* **타이포그래피**: Pico.css 기본 폰트 스택 그대로 (커스텀 폰트 추가는 4주 범위 밖)
* **다크모드**: Pico.css가 `prefers-color-scheme` 자동 대응 — 별도 작업 불필요

## 8. 미정 사항 — 함께 정해야 할 것

이 브리프에서 임의로 결정하지 않고 남겨둔 것들 (`.claude/rules/coding.md` "자동 구현 제한" 원칙에 따름):

1. **카드 배지 색상 5개 값** — `doc_type` 5개에 매핑할 실제 색상 코드
2. **"자세히 보기" 인터랙션 방식** — 카드 안에서 펼치기(아코디언) vs 별도 화면 전환
3. **빈 피드 상태** — 관련 정책이 하나도 없을 때 무엇을 보여줄지 (빈 화면 vs 안내 문구)
4. **정렬 기준** — 매칭 점수순 vs 최신순 vs 마감 임박순
